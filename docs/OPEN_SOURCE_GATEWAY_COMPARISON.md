# 开源统一网关对比与 LokToken 借鉴清单

更新时间：2026-09-07

本文基于 One-API、New-API 和 Sub2API 的公开仓库结构、文档与实现进行对比，目标是明确 LokToken 可以直接吸收的工程能力，不复制其项目定位或代码版权。

## 项目优势

| 项目 | 值得借鉴的能力 | 对 LokToken 的启示 |
|---|---|---|
| One-API | 渠道适配器目录清晰；模型与渠道能力矩阵；分组、权重、限流、余额监控；OpenAI 兼容接口覆盖广 | 将“上游差异”收敛在适配器和能力配置中，运营配置优先于改代码 |
| New-API | 在 One-API 基础上扩展多协议转换、自动分组、模型同步、Redis/内存缓存、异步任务；对计费数学、锁、跨数据库兼容和边界测试要求严格 | 计费、预扣、舍入、溢出、锁和重试必须有集中工具与回归测试；模型目录要支持自动同步和别名 |
| Sub2API | 订阅/账号池、额度策略、任务调度、面向实际用户的运营流程 | 若 LokToken 继续做商业化，可将“账号池/订阅池”和任务队列作为独立产品层，避免污染核心账本 |

## 已落地

本轮已实现稳定模型别名：

- `POST /admin/models/{model_id}/aliases` 创建别名。
- `GET /admin/model-aliases` 查看映射。
- `PATCH /admin/model-aliases/{alias_id}` 启停别名。
- `DELETE /admin/model-aliases/{alias_id}` 删除别名。
- `/v1/models`、`/v1/models/{id}`、聊天调用、生成任务和用户中心模型测试均解析别名。
- 别名只映射到 canonical 模型，计费、价格、健康检查和审计仍以 canonical 模型为准；停用或下架 canonical 模型会立即使别名不可调用。
- API Key 支持可选模型白名单：创建和轮换时继承，`/v1/models` 只展示允许模型，聊天/生成调用和门户测试统一拒绝越权模型；未配置白名单的旧 Key 保持兼容。

## 与热门项目的差距

### P0：兼容性和稳定性

1. **多协议转换**：当前主路径是 OpenAI Chat Completions；需要按真实客户优先级增加 Anthropic Messages、Gemini GenerateContent、OpenAI Responses，并为请求/响应/流式事件建立 golden fixtures。
2. **路由策略可解释性**：当前已有优先级、权重、熔断和失败切换；还需要把“为何选择该渠道、尝试了哪些渠道、每次失败分类”标准化暴露到 trace 和管理查询。
3. **分布式限流与缓存**：Redis 限流已有生产门禁；需要补全缓存命中策略、失效策略和多实例压测证据，避免把响应缓存误用于带工具或敏感上下文的请求。
4. **计费边界工具**：集中实现饱和转换、舍入和最大请求预算，拒绝超大 `max_tokens`、图像数量和视频时长，并把截断/拒绝写入审计。

### P1：运营效率

1. 模型自动同步后生成差异报告，支持批量启停、批量定价和审批发布。
2. 增加 Key/项目/组织级模型白名单、每日预算和并发上限。
3. 增加渠道余额定时刷新、低余额自动降权、渠道冷却和恢复指标。
4. 建立异步任务 worker、重试队列、死信队列和任务级 SLA；当前任务轮询仍依赖请求触发刷新。

### P2：商业化与生态

1. 企业 SSO/SCIM、组织配额、子账户、审批流和分账。
2. 正式支付、退款、发票和财务月结适配器。
3. OpenTelemetry trace、结构化日志、成本/毛利看板和租户级用量导出。
4. 供应商适配器 SDK 与贡献者测试契约，降低接入新厂商的维护成本。

## 建议的闭环顺序

1. 先完成多协议转换和 golden 测试，保证客户迁移成本可控。
2. 再完成 Key/项目模型权限、预算和并发保护，形成企业治理边界。
3. 然后建设异步 worker、缓存和完整观测，支撑规模化流量。
4. 最后接入支付、SSO/SCIM、分账和供应商生态，进入商业化扩展阶段。

## 需要用户配合的待办

- 提供首批必须兼容的 SDK/协议清单（OpenAI Responses、Anthropic、Gemini 的优先级）。
- 确认企业租户的配额口径：按组织、项目、Key 还是按模型分别限制。
- 提供真实供应商账单样例和支付/发票渠道要求，用于完成对账适配器。
- 确认是否建设 Sub2API 类订阅/账号池；若建设，需要单独定义账号来源、合规边界和风控策略。
